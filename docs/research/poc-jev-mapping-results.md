# PoC 結果: Jev によるフォームフィールド → プロフィール項目の対応付け

実施日: 2026-09-21
コード: `poc/`（実行方法は `poc/README.md`）
プロバイダ: OpenRouter 経由 `typesafe/jev-1.13-20260917`
生データ: `poc/results/run-2026-09-21T08-41-31-264Z.json`（第 1 ラウンド）、`run-2026-09-21T08-43-57-954Z.json`（第 2 ラウンド）

## 目的

拡張の中核設計「フォームのフィールドをコードが列挙し、各フィールドに『どのプロフィール項目を入れるか』を Choice で聞き、全フィールド分を 1 リクエストにまとめる（ワンショット fan-out）」が、日本語フォームで実用精度に達するかを確かめる。

## 方法

- フィクスチャ: 日本語 8 フォーム + 英語 1 フォーム、計 86 フィールド、正解ラベル付き（`poc/fixtures/forms.ts`）
  - EC 会員登録（17 項目）、問い合わせ（CF7 風）、Google フォーム風（`entry.NNN` の無意味な name）、求人応募、ホテル予約（電話・郵便番号の分割入力）、自治体イベント申込（ローマ字 name）、英語チェックアウト、ログイン画面、カード入力画面
- プロフィール項目: 26 種（`poc/profile-fields.ts`）。**値は送らず、項目名 + 英日併記の説明のみ**
- ガードレール: `is_payment` / `is_login` の Noul を同じリクエストに同送
- state の組み立て方を 5 バリアントで比較

| バリアント | state の fields | 質問の参照方法 | 項目の説明文 |
|---|---|---|---|
| full | 配列、全メタデータ | `fields[12]` | 各質問の criteria に埋め込み |
| label-only | 配列、label + tag/type のみ | `fields[12]` | 各質問の criteria に埋め込み |
| full-ref | 配列、全メタデータ | `fields[12]` | `state.profile` に 1 回だけ、criteria は null |
| **keyed** | **id キーのオブジェクト** | **`fields.f12`** | `state.profile` に 1 回だけ |
| inline | 配列（文脈用） | 質問の instructions オブジェクトに対象フィールドを埋め込み | `state.profile` に 1 回だけ |

## 分かったこと

### 1. 日本語精度は問題ない

公式ドキュメントは「CJK は精度が低い」と注意しているが、このタスク（ラベル・属性からの項目分類）では日本語 99%・英語 100% で差がなかった。日本語ラベルだけ（`label-only`）でも 91%。`name` / `autocomplete` 属性が付いていればさらに上がる。

### 2. 配列インデックス参照は 10 番目あたりから信用できない（最重要の知見）

`fields[12]` のような参照では、長いフォームの後半で**回答が 1 つ隣のフィールドにずれる**現象が再現性をもって発生した（2 回とも同じ位置・同じ誤答）。

```
f12 生年月日(年) → birth_month  ← f13 の正解
f13 月           → birth_day    ← f14 の正解
f14 日           → gender       ← f15 の正解（確信度 0.99）
f15 性別         → none         ← f16(メルマガ) の正解
```

意味の取り違えではなく位置ずれであり、確信度が高いため閾値で弾けない。英語フォームでも `Company (optional)`（index 9）→ `birth_date`（index 10 の正解）が同じパターンで出た。

`fields` を id キーのオブジェクトにして `fields.f12` で参照する（`keyed`）と完全に消え、17 項目フォームが 17/17・確信度 1.00 になった。

### 3. 説明文は state に 1 回置けば十分

各質問の criteria に説明文を繰り返す（`full`）より、`state.profile` に 1 回だけ置いて criteria を null にする方が、トークン半減（9.6k → 4.1k）で精度は同等以上。

### 4. ガードレールは明確に分離する

| ページ | is_payment | is_login |
|---|---|---|
| ログイン画面 | 0.02 | 0.97〜0.98 |
| カード入力画面 | 0.99 | 0.02 |
| それ以外の 7 フォーム | 0.01〜0.02 | 0.01〜0.03 |

閾値 0.5 で 54/54 正解。同じリクエストに同送するだけなので追加コストはごく僅か。

### 5. 残った「誤答」

`keyed` / `inline` で唯一残ったのは `カード名義（ローマ字）→ full_name`（正解ラベルは `none`）。ローマ字氏名をプロフィールに持つ以上、意味的には妥当な判断で、かつ同じリクエストで `is_payment = 0.99` が発火するため製品上は自動入力を止める。実害なし。

### 6. 再現性・速度・コスト

- 同一リクエストを 2 回投げてもほぼ同じ答え・確率（決定的に近い）
- レイテンシはフィールド数に依存せず p50 ≈ 300ms（2〜19 質問）
- 1 フォームあたり約 4,000 入力トークン ≈ $0.00017 ≈ 0.025 円

## 設計への反映（確定事項）

1. ワンショット fan-out（1 フォーム = 1 リクエスト）で実装する。エージェントループは不要
2. `state.fields` は **id をキーにしたオブジェクト**にし、質問は `fields.<id>` で参照する。配列は使わない
3. プロフィール項目の説明は `state.profile` に 1 回だけ置き、各質問の criteria は `{ key: null }` にする
4. Jev に送るのはフィールドのメタデータ（label / name / autocomplete / placeholder / type / section / options 先頭数件）と項目名だけ。**プロフィールの値は送らない**
5. `is_payment` / `is_login` の Noul を同送し、閾値 0.5 以上なら自動入力を停止してユーザーに確認する
6. `none` を必ず選択肢に含め、確信度 < 0.7 のフィールドは入力しない（precision 99〜100%）
7. `password` / `file` / `hidden` は観測段階で除外する

## 未検証（次の PoC 候補）

- **select の選択肢マッチング**: プロフィール値「東京都」→ `<option>` の選択。まずコードで正規化一致、外れたら Choice にフォールバックする方式の検証
- **分割入力の扱い**: 電話番号 3 分割・郵便番号 2 分割へ、値をどう分配するか（Jev は全部 `phone` / `postal_code` と正しく答えた。分配はコード側の責務）
- **実 DOM からの抽出**: 実サイトの content script でラベル解決（`<label for>`, `aria-labelledby`, 隣接テキスト, `<th>`）がどこまで効くか。jev-browser NOTES.md の落とし穴リスト参照
- **極端に長いフォーム**（50 項目超）でのトークン・精度
- TypeSafe 直接エンドポイントでの挙動確認（今回は OpenRouter 経由のみ）
